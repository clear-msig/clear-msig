# ClearSig security, flow and interface review — 2026-09-30

Base: `f74521ec88dca7db697053f42c23313d724ad9d0` (main). Changes are local and have not been pushed, merged or deployed. This review is a substantial hardening pass, not a guarantee of security or perfect functionality. Real wallet signatures, payments, exchange orders, production data and account credentials were not used.

## Highest-impact fixes

### Critical / high: money-moving trust boundaries

- **Settlement could trust fabricated deposits and self-asserted user IDs.** Settlement now authenticates Dynamic RS256 sessions against pinned environment/issuer/audience, derives ownership from the signed subject, and independently verifies native-chain deposit evidence from operator-configured RPCs. Claims are bound to the intent, reference, sender, receiving treasury, network, asset, exact amount, successful transaction and finality. A caller's `finalized`, amount or confirmation count is not evidence. Database constraints and locked state transitions prevent reassigning verified deposits to other intents.
- **Checkout, webhook and payout races could duplicate or regress work.** Webhook authentication precedes inbox persistence; invalid signatures cannot poison deduplication. Provider/reference/currency/amount and quote-funding deadline must match. Checkout and payout attempts are reserved durably before external calls. Uncertain side effects are not automatically repeated; they require reconciliation. Fast webhooks cannot be overwritten by slower worker responses.
- **Generic typed execution and the old remote status-only instruction could consume an approved v4 proposal without doing its action.** Both paths now reject v4. Dedicated action executors remain available; legacy compatibility is tested explicitly with historical v3 fixtures. The remote status-only tests are no longer presented as proof of actual Ika execution.
- **Chain binding accepted unrelated payers.** Bootstrap binding now requires the wallet's recorded creator. Browser membership alone does not authorize binding; the member gateway refuses this operator/bootstrap path. A quorum-governed binding protocol is a separate future version.
- **Private API access relied on forgeable headers.** Private agent routes now verify a signed session and fresh canonical on-chain membership before storage access. Pro metadata and unsigned sponsored wallet/chain routes also require a server-only gateway credential at direct Axum ingress. The Next gateway verifies user authority before forwarding that credential; it is never sent to browsers.
- **External agent execution lacked the on-chain-to-venue authorization bridge.** Added versioned order/settlement contracts, canonical wallet-to-dedicated-account binding, threshold-per-trade checks, exact route/order commitments, bounded grants, observed-risk requirements, atomic protective-order requirements, durable lease/reconciliation ports and short-lived server capabilities. Real external submission remains fail-closed until reviewed real ports and account configuration are connected. Paper and review workflows remain separate.

### High / medium: authentication and state integrity

- Owner approvals now bind exact action/target and complete canonical details, rather than truncated readable text alone. Legacy approvals are display-only; they cannot authorize new operations. Sessions/proposals cannot be resurrected, silently expanded or retargeted through alternate mutation routes.
- External signal HMAC v2 binds canonical target, network/program, raw payload, nonce and timestamp. Management requires a current member session. Nonce receipts survive inbox deletion/import.
- Agent local and server state use canonical v2 scopes; old name-only data and credentials are preserved without automatic reassignment. Local route children remain unmounted until the current identity and wallet scope resolve. Limited ownership-confirmed recovery copies paused profile text, not keys, grants, approvals or trades.
- Email routes now require authenticated sessions; invitations additionally require a verified inviter wallet and current on-chain governance membership. Self-notifications go only to a verified email credential. Branded links use deployment configuration, not attacker-controlled request headers.
- Untrusted RPC account bytes no longer become Rust enum/bool values through unchecked casts. Lengths are checked before allocation. Destination response sizes, rate-limiter cardinality/counters and streamed request sizes are bounded. Reconciliation rejects malformed or mismatched chain evidence.
- Same-name wallets no longer resolve by arbitrary RPC order. Owners and canonical PDAs are checked. Legacy name-addressed Pro APIs fail closed on globally ambiguous names.
- Solana read fallback no longer silently switches a custom/mainnet RPC to devnet, retries uncertain submissions or changes synchronous subscription IDs into promises. Fallback genesis identity must match; credential-bearing endpoint URLs are not logged.

## User-flow and performance fixes

- Batch input preserves all supported decimal places with integer arithmetic. Negative/exponent/malformed/over-precision values are rejected rather than rewritten. The composer and executor share the 16-recipient limit; imports are not silently truncated. Reviewed amounts and totals stay exact.
- Synchronous admission and cancellation guards prevent duplicate batch/dashboard actions. Late wallet responses cannot start the next step after cancellation. Uncertain submissions are shown as uncertain, not safely failed or completed.
- QR sessions stop immediately on dismissal, ignore late results, release media tracks and avoid unnecessary camera restarts. Same-origin camera policy still requires browser consent. Focus trapping, Escape, selects, tooltips and labelled errors were corrected.
- Recurring schedule retries persist the exact pending operation, including revoke versus activate, policy version, timing, count and token accounts. Reload/retry does not infer activation or request a new signature. Legacy ambiguous retry records fail closed.
- Recovery helpers reject confirmed transaction errors before saving attestations or showing success. Import secrets are cleared on terminal paths, and ambiguous post-submission outcomes require status review rather than reusing a wiped key. Abandoned approval collection ignores late work.
- App-lock hydration no longer briefly mounts protected content before checking the gate.
- Proposal listing now uses two wallet/discriminator-filtered reads, bounded intent mapping and owner/PDA validation instead of deriving the full intent × historical-counter Cartesian product. Tests cover sparse histories, huge counters, malformed/foreign accounts, errors and deterministic ordering. This is a verified complexity/RPC-count improvement, not a production latency benchmark.

## Interface direction

The user-supplied mobile screenshot and deployed public landing/chooser were inspected. The new local design retains ClearSig's identity while replacing dominant neon areas with neutral surfaces and restrained sage accents, reducing competing hero content and repetitive motion. Landing sections progressively reveal without hiding essential app controls; no-JavaScript and reduced-motion content remains readable. Shared theme tokens, opacity utilities, form semantics, focus and feedback surfaces were consolidated. See [calm interface rationale](../design/calm-interface.md) for official Apple/OpenAI references and implementation details.

**Visual verification limit:** the local Next app compiled and served HTTP 200, but Chromium could not launch because this execution runtime denies its Unix socket, including after the approved scoped escalation. No local desktop/mobile browser screenshot is claimed. Uploaded-reference inspection, deployed-baseline inspection and SSR/contrast/accessibility tests are distinct from a full responsive visual acceptance pass.

## Rollout prerequisites and remaining gates

1. Review the patch and rerun CI for its actual commit before deployment. None of these local fixes changes the currently deployed devnet program or services.
2. Deploy the rebuilt program only through a separately approved release. Bootstrap binding is creator/operator-only; member browser access is intentionally insufficient.
3. Configure matching **server-only** `CLEAR_MSIG_BACKEND_GATEWAY_TOKEN` on Next and Axum. Provision real credentials separately. Private metadata and sponsored creation fail closed without it.
4. Configure trusted Dynamic environment/audience and network identities. Connected hardware wallets without an authenticated Dynamic session cannot use private server services; there is no devnet bypass.
5. Apply settlement migration `0003_verified_deposit_evidence.sql`. Existing self-asserted deposit rows are not promoted to verified evidence.
6. Paystack and Korapay adapters are retained. No replacement provider was selected or activated. The immutable executable-quote port defaults to unavailable: a reviewed trusted pricing adapter is still needed before new money-moving settlement intents can be created. Indicative browser prices are never payout authority.
7. Token/shielded deposits and Solana CPI deposit shapes remain unsupported. Referenced native deposits must use the supported memo/calldata/OP_RETURN shape; the ordinary ClearSig Send screen does not yet attach that reference and is not offered as a compatible shortcut.
8. External agent execution and settlement-proof promotion remain disabled until exact trusted-chain/venue adapters, dedicated account bindings, protection semantics and live integration checks are reviewed. No financial accounts or API grants were provisioned.
9. New scoped state and HMAC v2 require integration re-registration/migration. Old state is preserved, not blindly imported as current authority.
10. Resolve unknown external attempts manually with independently verified receipts. Do not resume them by blindly retrying a transfer.
11. Complete actual desktop/mobile browser QA, authenticated account-switch flows and hardware/passkey/wallet integration in a browser-capable test environment.
12. Moderate npm advisories and documented Rust maintenance/unsoundness debt remain; see [dependency risk](dependency-risk.md). A passing configured policy does not mean all transitive debt disappeared.
